# Repository Guidelines

## Project Structure & Module Organization
- `src/`: CUDA/C++23 implementation.
  - `tensor.cc`: `Storage`/`Tensor` (bf16-first) and safetensors loading via simdjson.
  - `kernel.cu`: raw CUDA kernels (GEMM/GEMV, softmax, RMSNorm, RoPE, GQA scores/output, argmax) plus their `launch_*` wrappers.
  - `layer.cc`: host-side layer construction, `ScratchPad`/`LayerContext`/`InOutBuffer` memory plumbing, `from_parameters` factories.
  - `layer.cu`: the `operator()` forward paths for `Dense`, `RMSNorm`, `GroupedQueryAttention`, `Qwen2TransformerBlock`, `Embedding`, `Sampler`, `LmHeadDense`.
  - `model.cc`: `Qwen2Model` — weight wiring, the producer thread, and token streaming.
  - `main.cc`: CLI chat driver (tokenizers-cpp for encode/decode).
- `include/`: public headers shared by library, tests, and benchmarks (`tensor.h`, `kernel.h`, `layer.h`, `model.h`, `cuda_utils.h`).
- `tests/`: GoogleTest cases (`kernel_test.cc`, `tensor_test.cc`, `layer_test.cc`) plus `.safetensors` fixtures in `tests/data`; paths resolved via `TEST_DATA_DIR`.
- `bench/`: Google Benchmark microbenchmarks (`gemv_bench.cu`).
- `scripts/`: maintenance utilities such as `create_test_data.py` (regenerates `tests/data` fixtures).
- Build artifacts live under `build/` (or any `build*/` dir, all gitignored); binaries land in `build/bin`, libraries in `build/lib`.

## Build Targets & Dependencies
- `qwen2kern`: static library from `tensor.cc`, `kernel.cu`, `layer.cc`, `layer.cu`, `model.cc`; exports `include/`.
- `qwen2chat`: chat CLI (`src/main.cc`), links `qwen2kern` + `tokenizers_cpp`.
- `unit_tests`: GoogleTest binary registered with `gtest_discover_tests`.
- `bench_gemv`: Google Benchmark binary for GEMV variants.
- Third-party deps are pulled by CMake `FetchContent` (googletest, simdjson, google benchmark, tokenizers-cpp) — the first configure needs network access and is slow.

## Build, Test, and Development Commands
- Configure: `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug` (use `Release` for anything perf-related).
  For other GPUs, pass `-DCMAKE_CUDA_ARCHITECTURES=<sm>` to override the default 89.
- Build everything: `cmake --build build`
- Run unit tests: `ctest --test-dir build --output-on-failure`
- Run the chat demo: `./build/bin/qwen2chat -w <weights.safetensors> -t <tokenizer.json>` (see `README.md` for the full flag list; `-m` prints tokens/s).
- Run benchmarks: `./build/bin/bench_gemv` (Release build only — Debug numbers are meaningless).
- Refresh test fixtures if needed: `python scripts/create_test_data.py`

## Coding Style & Naming Conventions
- C++23 with CUDA C++20; prefer modern features (ranges, aggregate initialization, `std::exchange`).
- Formatting uses `clang-format` (LLVM base, see `.clang-format`). Run it before committing for any touched C++/CUDA sources.
- File and symbol names favor lower_snake_case; types are UpperCamelCase, private members are `_prefixed`.
- Keep headers under `include/` and implementation in `src/`; put host-only logic in `.cc` and kernel-launching code in `.cu`.
- Keep device/host boundaries explicit; guard CUDA calls with existing `CHECK_CUDA`/`assert` patterns from `cuda_utils.h`.
- `.clangd` pins `--cuda-gpu-arch=sm_89`; update it alongside any default-arch change.

## Testing Guidelines
- Tests live in `tests/*_test.cc` and use GoogleTest/GMock; mirror production filenames where possible.
- Add new fixtures to `tests/data` (generated by `scripts/create_test_data.py`) and reference via `TEST_DATA_DIR` to avoid hardcoded paths.
- Exercise edge shapes and dtype constraints for kernels; prefer deterministic inputs to enable bitwise comparisons.
- New kernel fast paths (e.g. GEMV specializations) need a test that pins them against the general path.
- Run `ctest --test-dir build` before pushing; aim to keep runtime GPU-friendly (small tensors, short runs).

## Commit & Pull Request Guidelines
- Commit messages are prefixed with the modified component(s) only, not conventional-commit types (e.g., `tensor: ...`, `layer, model: ...`); keep them scoped and imperative. Older history uses conventional commits (`feat(model): ...`) — do not follow that style for new commits.
- Keep commits focused (one logical change each) and include rationale in the body if behavior shifts.
- Pull requests should describe intent, list key changes, note test results (`ctest` output), and link issues when applicable. CLI log snippets beat screenshots for verification.
